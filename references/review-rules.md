# 审核与流转规则

## 六个审核节点

完整七阶段流程在 1～6 结束后分别审核一次；第 7 阶段直接提供交付总结。简化流程仅保留实际执行阶段的节点。

| 当前阶段 | 核心审核问题 | 通过后进入 |
| --- | --- | --- |
| 1 | 需求、范围、操作与 AC 是否正确？ | 2 |
| 2 | 复用充分、方案简单、风险可接受？ | 3 |
| 3 | 改动合理、关键规则明确、异常完整？ | 4 |
| 4 | 任务无遗漏、依赖合理、完成标准可检查？ | 5（开始文件修改） |
| 5 | 按计划实现、检查真实、偏差和剩余项透明？ | 6 |
| 6 | 验收证据充分、回归结果明确、限制可接受？ | 7 |
| 7 | 交付总结是否包含真实验证、项目交接和必要的架构同步提醒？ | 终点 |

确认在对话中生效，不要求另建文档。每次只提出当前节点真正需要决定的问题，不机械重贴完整审核表。

## 用户回复的含义

- “通过，进入下一阶段”或同样明确的继续指令：批准当前结果并执行下一个阶段。阶段 4 的此回复即开始按计划开发的授权，不重复问能否改代码。
- “需要修改：…”：修订当前阶段，展示变更和受影响结论，留在当前节点；不把反馈当作批准。
- “返回第 N 阶段：…”：返回指定阶段；只说“返回上一阶段”时回到当前阶段的前一阶段。
- 阶段内澄清答案不自动等同于批准全部成果；“收到”、沉默、问状态也不等同于通过。上下文中意图清楚时不拘泥固定口令。
- 用户明确授权连续执行阶段范围时，保留授权并连续推进，只在范围外或出现新的关键决策时停下。不能将“按流程开始”解释为全部节点已获批准。
- 简化流程中的“下一阶段”指已确认路线里的下一项；省略阶段所承载的必要决策必须提前补齐。

## 上下文与变更

在对话维护最少状态：当前阶段、有效的需求/AC、已确认设计与计划、用户授权、待解决问题。新会话仅凭磁盘上的草案不能断言用户已批准；先寻找明确确认记录，关键确认确实缺失时再询问。

关键需求或设计改变时，指出哪些下游结论失效并重新审核受影响部分。不要整套流程重启，也不要沿用已经失效的计划。已写代码存在时，说明需要怎样调整，不自动回滚用户工作。

发现重大冲突时给出“问题 → 影响 → 推荐调整 → 需确认内容”，暂停相关修改。普通命名、局部实现、既定设计内缺陷修复由 Agent 完成，不逐项索要批准。

## 验收证据与结论

- **实际验证**：确实执行相关操作或测试，有可定位的命令/场景、结果和必要证据。
- **静态检查**：代码审阅、类型检查或构建只能支持其检查范围，不能替代没有运行的业务或交互验收。
- **未验证**：缺环境、权限、账号、设备、外部依赖或人工操作；明确原因与补验步骤。

AC 只有得到足以支持该项的实际证据才标“通过”。测试失败、运行不了、未覆盖或靠推断的结果均不能写为通过。修复后必须复测相关失败项和受影响回归；未经复测，问题仍待验证。

| 结论 | 适用条件 |
| --- | --- |
| 通过 | 必需 AC 均已实际通过，必要相关回归/工程检查完成，无阻断问题 |
| 有条件通过 | 核心 AC 已通过；只剩非关键限制或未验证项，明确条件、影响与补验办法，并由用户接受。接受前注明“建议，待用户确认” |
| 不通过 | 关键 AC 失败或未验证、存在阻断缺陷，或交付依据不足 |

用户要求带限制交付时如实沿用这些结果，不把用户接受风险改写成“测试通过”。没有相应测试条件时交付可执行的手工验收步骤，不伪造运行记录。

## 输出裁剪

只输出当前阶段的必需产出；不重复已确认全文，不输出无关章节，不为凑完整而增加工作。默认用简短结论、少量列表和必要表格，详细内容按需展开。
